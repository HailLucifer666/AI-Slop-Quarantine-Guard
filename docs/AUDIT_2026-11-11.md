## C1 (medium) — The PR gate reports success when it could not read the PR

**Where:** `api/app/github_client.py:53-60` and `api/app/worker.py:188-196`.

**What the code does, mechanically.** The entire PR analysis depends on one fetch, `fetch_pr_diff`. It
makes a **single GET with no retry**, and maps **every non-200 (429/5xx/403/404) to `None`** — the same
value the caller needs for "this PR has no changes". `_run_pr_analysis` treats `None` as exactly that and
completes the check run with conclusion **`success`** and the text "✅ Nothing to analyze in this change."
No coverage record is built and no failure event is recorded; nothing in source ever re-drives the
analysis. Transport errors behave correctly (they raise and resolve to `action_required`), so the
fail-open trigger is specifically a non-200 response. The module's own retry-budget comment
(github_client.py:12-18) promises this class of transient failure will never silently disable the gate;
every conclusion-gating sibling retries — this one does not.

**Why it is not hypothetical.** Reproduced with the repository's own suite (run twice, by two
independent reviewers):

```
pytest tests/test_analyze_pr_failure.py -q   → 3 passed
```

`test_successful_analysis_does_not_record_a_failure_event` **pins the fail-open direction**: a fake
`fetch_pr_diff` returning None produces `update_calls == [("octo/repo", 42, "success", "✅ Nothing to
analyze in this change.")]` with no events. The suite asserts the wrong boundary — passing, in the wrong
direction.

**When it bites.** A PR author times a push to any GitHub API non-200 — engineerable by diluting the
installation's shared API budget with queued PRs. If branch protection requires this check, the PR is
mergeable with zero gate signal and SQG001/SQG002 CERTAIN findings are invisible. Without branch
protection the demonstrated impact is a false green check run — still false, still unearned.

**The fix (verified).** Retry within the module's stated budget in `fetch_pr_diff`; in the worker, resolve
`None` to `action_required` with an honest "could not fetch the diff" summary. A genuine empty diff (200,
empty body) still flows through `parse_diff` to the earned, coverage-backed success — the discriminator
is HTTP status, not body content. The existing test's fake must be updated in the same change, plus a
red-first regression test pinning the corrected direction. Full sketch in `findings.json`.

## C2 (medium) — The boot guard accepts the repository's own public secrets

**Where:** `api/app/config.py:103-108` (validator); `infra/docker-compose.yml:34,52`,
`.env.example:16`, `docs/BUILD_GUIDE.md:149` (the public values); `api/app/main.py:112` (the gate they
unlock).

**What the code does, mechanically.** The fail-closed validator exists so production never boots with
forgeable webhooks — but it checks only **truthiness**. The repository ships public placeholder values
for that exact variable: `GITHUB_WEBHOOK_SECRET: dev_secret` as real environment variables in the compose
manifest, and `your_webhook_secret_here` in `.env.example` plus a build-guide instruction to write it
into the repo-root `.env` — the only env file the app loads. Flip `ENVIRONMENT` to production while
keeping a repo-taught value and the boot passes silently; `verify_github_signature` then authenticates
anyone who can read this public repo. No secondary gate exists anywhere: the secret is referenced in
exactly three functional places, the webhook route has no other dependency, and the worker never
re-verifies.

**Why it is not hypothetical.** Reproduced via permitted commands (run independently twice):

```
pytest tests/test_config.py tests/test_security.py -q   → 12 passed
# the suite's own test_production_with_both_secrets_set_is_valid passes with arbitrary values
python -I -B -c "...Settings(environment='production', github_webhook_secret='dev_secret', api_key='k')..."
# → constructs without error; 'your_webhook_secret_here' → constructs; '' → ValidationError (control)
```

**When it bites.** Operator flips production while retaining a repo-taught placeholder (plausible: the
build guide teaches exactly that value) + network reachability. Impact high (whole webhook
authentication bypassed; the worker holds the App private key), likelihood low (the flip is operator
behavior) → overall medium.

**The fix (verified judgment).** A placeholder denylist inside the same model validator, extended with
the three more committed placeholders Phase 5 found (`SECURITY.md:17`, `BUILD_GUIDE.md:527`,
`DEPLOYMENT.md:136`). The stronger alternative — rejecting any secret that appears verbatim in tracked
files — is infeasible at boot: the production image copies only `pyproject.toml` and `app/`, so the
running process cannot read the templates. Residuals stated honestly: novel weak values are not caught;
new templates must append to the list. Red-first tests included in `findings.json`.

## Needs-validation leads (19 — each with trace, exact blocker, and a bounded owner-run check)

Full records in `findings.json` / `NEEDS-VALIDATION.md` in the run directory. Every lead survived
independent verification (traces re-read line-by-line; blockers confirmed genuinely unanswerable on the
audit host). **These are leads: no severity, no block-eligibility, and nothing here feeds the Guard
without an executable PoC — the firewall in CONTRIBUTING.md applies to this document too.**

**Silent data loss / false pass (triage first — every one has a cheap owner check):**

- **L1 — `diff.parse-diff-header-lookalike-content-drops-and-misattributes`.** `parse_diff` classifies
  lines by string prefix only. An added line whose content begins `++ ` renders as `+++ ` and is consumed
  as a file header; `++ /dev/null` nulls the current file so **every subsequent added line is silently
  dropped from all eight analyzers — including CERTAIN block-eligible secret detection —** and the PR
  path then reports `success` with full coverage over the unanalyzed remainder (it hardwires
  `unexamined_count=0`, defeating the exact invariant the coverage module documents). `++ b/<path>`
  re-attributes the tail to an attacker-chosen path. One line hides a credential from the gate.
  Owner check: run the record's one-liner — `parse_diff('+++ b/x\n@@ -0,0 +1,2 @@\n++ /dev/null\n+LEAK=1')`
  returns `[]` per source.
- **L3 — `webhook.enqueue-connection-error-keeps-dedupe-claim`.** The dedupe claim is taken before
  enqueue; the ConnectionError branch returns 503 **without releasing the claim** (the generic branch
  does release). A claim whose LPUSH failed stays set for 24h, so GitHub's same-GUID retry is answered
  "duplicate" and the PR is never analyzed. The code's own comment and the tested invariant both promise
  the opposite; the test covers only a generic exception.
- **L5 — `worker.non-dict-job-dispatch-attributeerror`.** `json.loads` is guarded for JSON syntax only;
  a valid-JSON scalar/array job (or non-dict payload) reaches `job.get(...)` outside any except — the
  worker process exits. The scan-queue sibling is wrapped; only the webhook routing path is bare. With
  `restart: unless-stopped` each injected job is a crash-restart cycle.
- **L4 — `manifests.npmrc-root-only-private-scope-missed`.** npm's project-level `.npmrc` is hierarchical;
  the guard fetches only the root one. A scoped private package declared in a subdirectory is checked
  against the public registry, 404s, and is emitted as **CERTAIN, block-eligible "does not exist (404)"**
  — a false provable fact, the exact failure shape the G3 guard exists to prevent and the prior audit
  recorded as closed.

**Control plane:**

- **L2 — `queue.unauthenticated-job-injection`.** No Redis auth exists in any source config (compose
  publishes 6379 with no password; `run_redis.bat` starts no-auth). The worker trusts job JSON without
  binding to a scan row: a `{kind:scan, source:zip, ref:<path>}` job makes the worker **open and read any
  worker-readable file and delete it in a finally that runs even when the content is not a zip** — an
  arbitrary read+delete primitive that bypasses the API's upload boundary entirely — and injected webhook
  jobs mint GitHub installation tokens for attacker-chosen installation ids. Sibling controls prove the
  gap: `local` is re-gated, `url` is re-validated, `zip` alone accepts an unvalidated ref.

**Bounded-in / unbounded-out (L6-L12):** PR-path fetches return unbounded attacker-scaled content
(nine parses per job; the analyzer budget's own premise — the ingest caps — does not apply on this path);
`complete_scan` writes a findings row with no count or byte cap while per-line finding multiplication and
untruncated snippets make output orders of magnitude larger than input (a ≤50MB repo can produce a
0.5-0.95GB row, rehydrated whole by every read path); the zip ignore-spec pre-pass is the one entry read
that bypasses the decompression cap; pooled ignore patterns are uncapped and matched per path on the
worker event loop; **three per-line regexes admit quadratic backtracking and the sync-rule timeout
abandons threads that keep burning CPU — this contradicts the prior audit's own linearity claim**
(AUDIT_2026-08-22.md:154-155: "no nested quantifiers" cannot see a trailing `\s*$` re-scan per backtrack
position of a preceding `\s*`); the SQG007/SQG009 analyzer budgets are inert (their only awaits never
suspend); spooled zip uploads strand permanently with no sweeper when the worker never reaches ingest
(the compose dev stack strands **every** upload deterministically — api and worker never share /tmp).

**Deployment/supply-chain posture (L13-L17):** the Redis bootstrap downloads and **executes** the first
release zip with no checksum and trusts it forever after; the compose manifest commits the Postgres
superuser password (`password`) and publishes 5432 on all interfaces; all 21 CI `uses:` refs are floating
tags with no `permissions:` blocks anywhere; FastAPI serves `/docs`, `/redoc`, `/openapi.json`
unauthenticated in every environment (the spec says "/docs (dev)"; no code enforces it); the dashboard's
"Copy for AI" export pastes attacker-authored finding text (unfenced messages, unneutralized fences,
uncapped manifest keys) into a prompt the operator is invited to give an AI agent with write authority.

## Discovered while auditing

- **The prior audit's linearity check has a blind spot** (found via L6): "no nested quantifiers" does not
  detect the sequential-composition backtracking shape. The check's syntactic criterion, not the rules,
  is what needs widening — a timing test is the only honest guard for regex cost.
- **The suite pins two fail-open boundaries as intended behavior** (C1's None→success test;
  `test_config.py`'s accepts-any-non-empty test). Red CI is a full stop, but so is a green test asserting
  the wrong direction — both confirmed findings were *protected* by passing tests.
- **`start.bat` is broken as committed**: it launches `run_web.bat`/`run_api.bat`/`run_worker.bat`, none
  of which exist in the tree. A fresh clone completes setup and then never starts.
- **The compose dev stack cannot scan zips at all**: api and worker never share `/tmp`, so every upload
  fails in the worker while the spooled file persists in the api container.
- **Retention is documented but never enforced** — honestly disclosed in the Settings UI
  ("nothing is deleted yet"), contradicted by `docs/DATA_MODEL.md`. Docs drift, not a finding.
